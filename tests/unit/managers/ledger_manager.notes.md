## How the tests are built
- **Conventions → fixtures/helpers** (top of the test file, each commented with its convention):
  - W1/W2 → `w1`, `w2` (`make_workspace`); U1/U2/U3 → `u1`, `u2`, `u3` (`make_profile`). `M` → `LedgerManager()`.
  - M1/M2/M9, F1/F2/F9, I1/I2/I3/I9, PC1/PC2/PC9, A1/A2/A9 → local builders `mk_machine`, `mk_factory`, `mk_item`, `mk_project`/`mk_pc`, `mk_attachment` (none exist in `tests/unit/factories.py` yet; batch mode keeps them local — see "Factories added" below).
  - "machine entry" / "project entry" / "inventory entry" / "attachment entry" → `mk_mel`, `mk_pel`, `mk_il`, `mk_al`: each inserts one ledger row with workspace W1, performer U1 and a valid `transaction_type` by default, every other required column given a valid value, and takes an explicit `performed_at`.
  - "machine snapshot" / "inventory snapshot" → `mk_machine_item`, `mk_inventory` (the latter defaults `is_deleted=False`).
  - `T(d)` / `T(d, hh:mm:ss)` → naive 2025-06-`d` datetimes (machine/project/inventory ledger columns are naive `DateTime`). `TA(...)` → the aware-UTC variant for the attachment ledger's tz-aware `performed_at`.
  - Re-read → `reread_machine_item`, `reread_inventory` (`expire_all()` + fresh `SELECT … WHERE id`). "Other recorded columns unchanged" → `snap_machine_item`/`snap_inventory` snapshot a fixed set of non-mutating columns (captured once before the call, compared by equality after) — now used by LED-RMI-01/06 and LED-RINV-08 (previously defined but unused; see Revision history). Counts → `mel_count`, `pel_count`, `il_count`/`il_workspace_count`, `al_count`, `mae_count` (fresh `COUNT(*)`). "Latest entry" → `latest_mel`, `latest_il`, `latest_event` (ORDER BY id DESC, LIMIT 1, after the call — there is at most one new row per discrepancy case so this is unambiguous). `ids(rows)` compares lists by `.id`.
  - Base setups as named fixtures/functions: `ml_base` (ML-base), `pc_base` (PC-base), `il_base` (IL-base), `al_base` (AL-base), `im_base` (IM-base), `tu_base` (TU-base); `rm_entries`/`rm_base` (RM-base) and `ri_empty`/`ri_hist` (RI-empty/RI-hist) as fixtures, with a handful of RMI/RINV cases building a one-off variant inline (no snapshot, snapshot in W2, snapshot qty overridden) instead of parameterizing the fixture.
- **Mocks:** none, per the spec/Conventions. `utcnow` is not mocked; LED-RMI-07 brackets the real call with `t0 = utcnow()` / `t1 = utcnow()` and asserts `t0 <= performed_at <= t1`. Inventory-adjustment `performed_at` is asserted against `SELECT now()` run in the same transaction (LED-RINV-10) rather than against a Python clock.
- **DataError cases** (`*_negative_limit_raises`, `*_negative_skip_raises`, for GML/PCL/GIL/GAL): `with pytest.raises(DataError): with db.begin_nested(): M.<call>(..., limit=-1)`, then a fresh count query confirms nothing else changed.
- **Race simulations** (LED-RMI-16, LED-RINV-17): `StatementRecorder(engine)` attaches a `before_cursor_execute` listener (observe-only, per Conventions) and exposes `.statements`, the list of captured SQL text; the test then calls `any_select_for_update(statements, table)` to check the SELECT against `machine_items` / `inventory` (excluding `inventory_ledger`) carries `FOR UPDATE`. Both are strict xfail (BUG-643, BUG-644): today neither SELECT carries a row lock.
- **Tie-order cases, redesigned in revision 3 (BUG-640/641, spec G8):** the earlier data-only design (3 tied rows inserted ascending-id, expect descending-id back) was flaky — Postgres's tie-break for `ORDER BY performed_at DESC` alone is not reliably ascending-id (verify finding 1/2). Revision 3 instead proves the bug from the recorded SQL: `order_by_ends_id_desc(statements, table, with_limit=False)` (new helper, next to `any_select_for_update`) asserts at least one recorded `<table>` SELECT has an `ORDER BY`, then reports whether any of them has sort keys exactly `performed_at desc, id desc` (normalized: whitespace/case collapsed, table/alias qualifiers like `machine_item_ledger.` stripped — best-practice default D5) and, when `with_limit=True` (the "top-1" lookups GMB-05/GIB-06), a `LIMIT` after it. Verified empirically (see Self-check) that today's compiled SQL is always `ORDER BY <table>.performed_at DESC` with no second key, so `order_by_ends_id_desc(...)` is `False` on every run — the assertion is a deterministic strict-xfail trigger, not a chance one (D4). The tied-row data-order assertion is kept in the same test, after the SQL assertion, as documentation of the intended fix; it cannot XPASS the test by itself since the SQL assertion always fails first today.
  - List queries (ORDER BY ends with no required LIMIT, though one is always present since the manager always passes a `limit`): LED-GML-14, LED-PCL-04, LED-GIL-16, LED-GAL-10 (one table each), LED-IMS-07 (two tables: machine + inventory), LED-TBU-06 (three tables: machine + project + inventory — unreachable today, since `get_transactions_by_user` raises `AttributeError` on BUG-645 before any SQL for the call runs at all; written to be correct once BUG-645 is fixed, per the cases file).
  - "Top-1" latest-entry lookups (`with_limit=True`): LED-GMB-05, LED-GIB-06. LED-GIB-06 additionally crashes on BUG-655 (`entry.value_after` `AttributeError`) — but only *after* the SELECT executes and is recorded, so the SQL assertion (reached first) still proves the point; the call then raises before the data-order assertion is reached, which is fine (xfail only needs some exception/failed assertion, and the cases file's own reason already says the call still fails today for this reason).
- **Lock cases' other half:** the row-lock bugs are also covered by sequential two-call cases run in one session (LED-RMI-15 pass; LED-RINV-16 xfail via BUG-655 since any bucket with ledger history still crashes before the second call can prove anything) — matching the Reviewer summary's note that a true concurrent race cannot be simulated inside one rolled-back transaction.
- **BUG-655 blast radius:** every `reconcile_inventory` case that has ledger history is xfail, even when the case is really targeting a different rule/bug (R6a, R9b, R10, …), because `get_inventory_balance` raises `AttributeError` before any of that code runs. Only `reconcile_inventory` cases with an **empty** ledger bucket (snapshot vs. ledger-qty-0) pass today; this is called out case-by-case with "(and BUG-655)" in the xfail reason where applicable, matching the cases file.
- **New `get_transactions_by_user` cases (TBU-03/04/05/06), revision 3 wording fix:** these previously set up and asserted only the machine ledger although their Given/Then (now spelled out explicitly in the cases file, revision 3) cover all three ledgers. They now insert matching project/inventory rows at the same timestamps and assert `result["project"]`/`result["inventory"]` too, alongside `result["machine"]` — all of which stay unreachable today (BUG-645 raises before the dict is built at all) but are now faithful to what the case asks for once that bug is fixed.
- **Default-`limit=100` cases, new in revision 3** (LED-GML-20, LED-PCL-07, LED-GIL-19, LED-GAL-13): 101 rows inserted at one-minute increments, the call omits both `skip` and `limit`, and the result is asserted to be exactly the 100 newest (oldest row absent). Mirrors the existing LED-IMS-08 pattern.
- **xfail honesty:** verified with `--runxfail` for the full file (see Self-check) — every xfail fails first on the assertion/exception named in the cases file's "fails today on" (or, for the tie-order cases, on the new SQL `ORDER BY` assertion that proves the equivalent fact deterministically), and no test XPASSes.
