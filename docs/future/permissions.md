## Today

**Who is signed in, and which workspace**
- Every request needs a bearer JWT; `get_current_user` turns it into a `Profile` or answers 401 (`app/core/deps.py:34-78`).
- `get_current_active_user` checks nothing more: profiles have no active/disabled flag, so a user cannot be locked out of the whole product (`app/core/deps.py:81-97`; deps spec Q1, intended).
- The workspace comes from the `X-Workspace-ID` header only; the token's `workspace_id` claim is never read (`app/core/deps.py:120`; deps spec Overview).
- Workspace gate: an `active` membership (`workspace_member_dao.has_access`, `app/dao/workspace_member.py:60-67`), else 403 (`app/core/deps.py:149-156`).
- Subscription state (trial ended, cancelled) does not limit access (deps spec Q3, intended).

**Platform admins (Makorsha staff)**
- `profiles.is_platform_admin` (`app/models/profile.py:23`). A platform admin enters any workspace without a membership (`app/core/deps.py:145-147`).
- `get_platform_admin` guards the platform support inbox (`app/core/deps.py:161-170`; `app/api/v1/endpoints/platform_help.py:26,45`).
- Waitlist admin: platform admin, or an email in `WAITLIST_ADMIN_EMAILS` (`app/core/waitlist_admin.py:9-32`).

**Roles inside a workspace**
- `workspace_members.role` is free text (`app/models/workspace_member.py:22`). There are two different role lists in the code:
  - `RoleEnum`: `owner`, `finance`, `ground-team`, `ground-team-manager` (`app/models/enums.py:7-12`); used by `access_control.role` (`app/models/access_control.py:16`) and the role checks below.
  - `VALID_MEMBER_ROLES` = `owner, manager, member, viewer, ground-team` (`app/schemas/workspace_member.py:6`) and `VALID_INVITE_ROLES` = `manager, member, viewer, ground-team` (`app/schemas/workspace_invitation.py:6`); used when adding, inviting and re-roling members (`app/managers/workspace_manager.py:189,334`; `app/schemas/workspace_member.py:59`).
  - So, read in the code (not run): invitations and role changes cannot give `ground-team-manager` or `finance`, though help tickets, projects and member removal check for `ground-team-manager`. Not logged as a bug yet.

**Owner-only actions today**
- Update the workspace, change a member's role (`app/services/workspace_service.py:131,176-184`); other owner-only actions through `_require_owner` (`app/services/workspace_service.py:60-67`).
- Cancel an invitation (`app/managers/workspace_manager.py:543`).
- Reset another member's password (`app/services/auth_service.py:826`).
- Approve or reject a risk-held payment (`app/api/v1/endpoints/payments.py:108-110`).
- Member removal: owner cannot be removed; `ground-team` cannot remove anyone; `ground-team-manager` can remove only `ground-team` (`app/managers/workspace_manager.py:275-283`).

**Record-level rules (the only places a record has its own visibility)**
- Projects: `visibility` is `workspace` or `invited_only` (`app/models/enums.py:39-42`). A private project opens for the workspace owner, an active `owner`/`ground-team-manager`, its creator, or a project member (`app/managers/project_manager.py:27,61-93`); others get **403** "You do not have access to this project" (`app/managers/project_manager.py:111-124`). Components follow their project (`app/managers/project_manager.py:126-146`).
- Help tickets: platform admin, `owner` / `ground-team-manager`, or the creator may open a ticket (`app/managers/help_ticket_manager.py:16-19,38-48`); others get 403 (`app/managers/help_ticket_manager.py:64-65`; `app/api/v1/endpoints/help_tickets.py:97,125`). Whoever may open it may also edit it (OQ-8).
- Orders: only an assigned approver may approve (403 "You are not an assigned approver for this order": `app/managers/purchase_order_manager.py:1572-1578`, `expense_order_manager.py:544-551`, `transfer_order_manager.py:695-701`, `sales_manager.py:819`, `work_order_manager.py:708`).
- Invoices: per-account and per-invoice locks, not per-person (`app/managers/account_invoice_manager.py:103-105`; `app/managers/invoice_payment_manager.py:84-89`).
- System tags cannot be changed or deleted, by anyone (`app/services/item_tag_service.py:64,82`; `app/services/account_tag_service.py:57,75`).
- Everything else: any active member may read and change everything in the workspace (no other 403 in `app/`, grep of `HTTP_403_FORBIDDEN` / `PermissionDeniedError`).

**Permission table (`access_control`)**
- Rows of `type` (`page`, `manage-order-status`, `feature`) + `target` + `role` per workspace (`app/models/access_control.py`; `app/models/enums.py:15-19`).
- All CRUD endpoints need only an active membership (`app/api/v1/endpoints/access_control.py:20-79`); nothing in the backend reads the rows to allow or refuse (access_control DAO spec FU-1 (b); OQ-4).

## Decided already

- **OQ-1 — email identifies one account whatever its capitals.** Compare `lower(trim(email))`, store lower-cased, unique index on `lower(email)`, script lists existing pairs for manual merge. → BUG-1860, BUG-1861, BUG-1862.
- **OQ-4 — only the workspace owner may create, change or delete permission rows** (403 otherwise); any member may read. → BUG-1875. Whether the table becomes enforcing is left to this feature (moved notes above).
- **OQ-5 — attachments, discussions and calendar entries follow the record's own visibility**; a member who cannot open the private project or help ticket gets 404 / does not see it. → BUG-1867 (project discussions), BUG-1868 (help ticket discussions), BUG-1869 (calendar), BUG-1870 (attachments).
- **R9a — mentions on such records skip people who cannot open them** (no notification, no preview). → BUG-1879 (decided by Claude as a consequence of OQ-5; `discussion_service.spec.md` `create` R9a).
- **OQ-8 — only a help ticket's creator edits its title, description, category**; owner, ground-team-manager and platform admins may still close / reopen. → BUG-1863.
- **OQ-11 — a stamp image is accepted and deleted only under the user's own `profiles/<id>/stamp-` prefix**, else 400. → BUG-1864, BUG-1865.
- **OQ-12 — the server builds the stamp's `url` from the accepted `public_id`.** → BUG-1866.
- **Calendar amounts** — every member sees invoice and order amounts on the calendar; owner: keep as a note for this feature (`calendar_service.spec.md` FU-2; moved notes above). No rule changed.
- **HR-16 — nothing links across workspaces**; such links are refused as "not found", and no response shows another workspace's ids or names (`docs/testing/house-rules.md`).
- **Non-members cannot probe workspace ids**: a non-member (not platform admin) gets the same 404 as for a missing workspace. → BUG-440 (deps spec Q2, reviewer).
- **No product-wide "disable user" switch** — intended for now (deps spec Q1, reviewer).
- **Subscription state does not gate workspace access** — intended for now (deps spec Q3, reviewer).
- **Waitlist admin = platform admins only**; the email allowlist grants nothing; one refusal message for all. → BUG-540, BUG-541 (waitlist_admin spec Q1, Q2, reviewer).
- **A platform admin's workspace ticket list shows every ticket**, matching what they can open by id. → BUG-1578 (help_ticket_service spec Q2, reviewer).
- **A removed member is taken off pending approvals, projects, and open work order assignees**, with events. → BUG-1201 (approvers, owner), BUG-1280 (project members), BUG-1883 (OQ-6, owner).
- **Order templates**: department and default approver must belong to the caller's workspace. → BUG-1216 (order_template DAO FU-1 (a)).
